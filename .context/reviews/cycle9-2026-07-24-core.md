## Finding

### CORE9-01 — Export eligibility and estimates can use a different duration from the request

- **Severity:** Medium
- **Confidence:** High
- **Status:** Confirmed source and component-state defect
- **Primary source:** `src/components/ExportPanel.tsx:111-164,241-263,483-505,569-598`
- **Downstream guard:** `src/lib/videoEncoder.ts:7,113-132,157-173`
- **Existing test gap:** `src/components/ExportPanel.test.ts:288-339`;
  `e2e/travelback.spec.ts:3177-3203`

#### Causal trace

Cycle 5 correctly split the editable string `durationDraft` from the committed
numeric `duration`. The split left two authorities in the same export
transaction:

1. `safeDuration`, the output and memory estimates, `exportTooLarge`, and
   `canStartExport` are derived only from committed `duration`
   (`ExportPanel.tsx:144-164`).
2. A valid edit changes only `durationDraft` until blur, Enter, or Start
   Export (`:241-255,483-505`).
3. `handleExport` checks the old `canStartExport` first, parses/queues the
   draft commit second, and immediately sends the parsed draft to `onExport`
   (`:257-263`). A React state update cannot recompute the gate inside that
   invocation.

This always creates a visible mismatch while a valid draft remains focused:
the field can show one duration while the displayed file/memory/time estimates
and Start button still describe the previous duration. It also makes the
handler unsafe for activation paths that do not first move DOM focus and fire
blur (for example an accessibility or synthetic button activation).

The mismatch crosses a real safety boundary. With the default 1080×1920
resolution, 30 fps, and Maximum quality (20 Mbps), the current estimator gives:

- 10 seconds: 23.84 MiB encoded and 87.14 MiB estimated memory, so Start is
  allowed;
- 180 seconds: 429.15 MiB encoded and 492.76 MiB estimated memory, so Start
  must be blocked by the 256 MiB cap.

Starting from a committed 10 seconds, typing `180` without first committing
therefore leaves the UI on the allowed 10-second state. Direct activation of
Start in that state passes the stale gate but calls `onExport` with 180
seconds. The encoder independently recomputes the 180-second memory estimate
and throws `EXPORT_TOO_LARGE` at `videoEncoder.ts:171-173`, after the export
controller has already acquired its lease, paused playback, resized the map,
and waited for it to settle. The encoder guard prevents an over-budget
allocation, but the panel admitted a job it already had enough information to
reject.

Ordinary pointer activation commonly blurs the number field before `click`,
which can mask the launch half of this defect in that input path. It does not
remove the focused-field estimate mismatch, and the handler still has no
self-consistent prospective eligibility check.

#### Fix

Parse the draft once into a prospective duration and use that same value for
all derived estimates, the too-large decision, button eligibility, and the
request. An invalid draft should make Start unavailable while retaining the
current associated range error. As defense in depth, `handleExport` should
recompute eligibility from its parsed duration rather than relying on a render
closure computed from a different value.

Add a focused component regression that:

1. begins with a feasible committed 10-second duration;
2. selects Maximum quality and enters `180` without a separate blur/Enter;
3. asserts that estimates and the too-large warning already describe 180
   seconds and that activation cannot call `onExport`; and
4. enters a feasible value and asserts that the estimates, eligibility, and
   exact request duration agree.

The current component test commits `15` with an explicit `focusout` before
Start, while the browser regression validates with Tab/Enter and never crosses
the memory gate. Neither exercises the divided-authority state.

This is distinct from Cycle 5's recorded root. That finding was immediate

moving the pre-existing estimates and safety gate to the same transaction.

## Rejected hypotheses and deduplication

### File/sample import handoff while awaiting export settlement — rejected

A first import can pass its generation check and await
`loadTrackIntoSession()` → `cancelExportAndWait()`, but no ordinary newer file
intent can make the first request win afterward:

- an active export keeps the application root inert behind the export modal;
- without a lease, `cancelExportAndWait()` returns immediately;
- when two loads do share one settlement, their promise continuations are
  registered in intent order, so the later load commits last.

The upload component also aborts and generation-invalidates parsing before
starting the next intent. No deterministic supported interaction produced a
stale final track, so this was not promoted.

### Scene camera preview can overwrite a committed keyboard/pointer value — rejected

For keyboard changes, the commit occurs before the preview is scheduled, and
keyup cancels an unapplied frame or restores the latest committed camera after
an applied preview. Pointer settlement ends preview ownership before publishing
the changed scene, after which the parent applies the committed scene camera.
Cancellation restores the origin. The current rAF/ref ordering therefore did
not support the suspected stale-camera result.

### Other challenged candidates — not new

- Dense Google/KML intermediate allocation, conservative pre-dedup point
  budgeting, partial timestamp ordering, strict base-path grammar, and
  finalizer cancellation limitations are already recorded or explicitly
  accepted boundaries.
- Full-range trim scene invalidation, scene percentage partial-entry behavior,
  timeline terminal-event coverage, and earlier codec-probe recovery concerns
  are historical roots rather than new Cycle 9 findings.
- The three native/host process-containment residuals remain the recorded
  Cycle 2 platform boundaries and were not relitigated.
