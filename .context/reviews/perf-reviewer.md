# Perf Review — Prompt 1

## Overall impression
The app is pretty solid for normal-sized tracks, but a few structural choices make it pay a lot of extra CPU/GPU/memory cost exactly where users feel it most: live playback, export, and large JSON imports. The worker exists, memoization exists, and the UI is thoughtful — but the hot paths still do too much work on the main thread and too often.

**Grade: C+**

## Findings

| # | Location | Concrete slowdown scenario | Why it happens | Suggested fix | Confidence | Status |
|---|---|---|---|---|---|---|
| 1 | `src/components/MapView.tsx:500-506` | On every normal map session, the live map canvas keeps paying the WebGL backbuffer tax even when no export is happening. On lower-end laptops/phones this can shave FPS and raise GPU memory pressure. | `canvasContextAttributes: { preserveDrawingBuffer: true }` is enabled for the always-mounted map canvas, which disables an important rendering optimization across the whole session. | Make drawing-buffer preservation export-only, or use a separate export canvas/map instance so ordinary browsing stays on the fast path. | High | Confirmed |
| 2 | `src/lib/parser.ts:532-563` + `public/workers/trackParser.worker.js:125-271` | Importing a large Google Location History JSON file can freeze the tab before parsing completes, especially near the 500MB limit. | The file is read into one giant string on the main thread with `FileReader.readAsText`, then that same string is structured-cloned into the worker. That duplicates memory and work before JSON parsing even begins. | Read as `ArrayBuffer` and decode in the worker, or stream/chunk the file; if browser memory is the real ceiling, lower the accepted JSON cap. | High | Confirmed |
| 3 | `src/lib/videoEncoder.ts:72-85` + `src/lib/useExportController.ts:138-145` | Exporting a long or high-resolution video can consume a lot of RAM at once and stay resident after export completes. | The encoder uses `BufferTarget` with `fastStart: 'in-memory'`, so the whole MP4 is buffered in JS memory. The controller then wraps that buffer in a `Blob` and stores it in React state for preview/share. | Prefer a file-backed or streaming target when available; for large exports, avoid retaining the full blob in React state unless the preview really needs it. | High | Confirmed |
| 4 | `src/app/page.tsx:32-419` + `src/lib/usePlaybackController.ts:19-40, 89-93, 123-170` | While playback or export is running, the entire page tree rerenders every animation frame, including overlays and hidden panels that do not need the progress tick. | `progress` lives in `HomeInner`, and `setProgress` is called from RAF. Because the top-level page owns almost all chrome, every tick reruns the full tree instead of only the progress-sensitive subtree. | Split static chrome from the playback subtree, or memoize/move the playback-driven UI so only the components that truly need `progress` rerender each frame. | High | Confirmed |
| 5 | `src/components/MapView.tsx:754-777` | During playback, the trail line is rebuilt from scratch on every frame. On long tracks that means a lot of slice/map/object churn at 30–60 FPS. | The effect recomputes a brand-new GeoJSON geometry with `buildTrackGeometry(...)` and sends it through `setData` every tick, so work scales with track length and frame rate. | Keep a precomputed geometry and reveal progress incrementally, or use a style/shader approach that avoids rebuilding the full traveled line each frame. | High | Confirmed |
| 6 | `src/components/SceneEditor.tsx:201-285, 458-492` | Dragging a scene slider can feel sticky on weaker devices because every pointer move triggers state normalization plus a live map preview. | `updateScene` commits immediately on each `onChange`, `commitScenes` re-normalizes/sorts the scene list, and parameter changes call `onPreviewScene` while the user is still dragging. | Separate draft vs committed scene state, debounce preview updates, or only apply the preview on pointer-up. | Medium | Confirmed |
| 7 | `src/app/page.tsx:240-243`, `src/components/TimelineSelector.tsx:63-69`, `src/components/ElevationProfile.tsx:23-26`, `src/components/Controls.tsx:42-44`, `src/lib/videoEncoder.ts:65` | Loading or slicing a very large track repeats the same O(n) cumulative-distance scan several times, so a 100k-point file gets walked and allocated more than once before the UI settles. | The same distance table is computed independently in the page, timeline selector, elevation profile, controls, map view/export paths, instead of being shared once per track/session. | Compute and cache one distance table per track load, then pass it down or store it with the track/session object. | Medium | Likely |

## Final sweep

I did not find another high-confidence runtime bottleneck that beats the seven issues above. The largest remaining static asset is `public/fonts/PretendardVariable.woff2` at ~2.06MB, but `font-display: swap` softens the first-paint impact, so I did **not** count it as a finding. The 5 map-style JSON files are also a noticeable asset budget, but they are secondary compared with the main-thread/export hot spots above.
