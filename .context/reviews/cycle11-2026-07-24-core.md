## Finding

### CORE11-01 — Imperative camera publication leaves the smoothing authority stale

Severity: **Low**

Confidence: **High**

Evidence:

- `src/app/page.tsx:513-533` computes the camera using the newly requested
  duration and publishes it through `MapViewHandle.applyCameraState`.
- `src/components/MapView.tsx:287` retains the declarative smoothing origin in
  `lastCameraStateRef`.
- `src/components/MapView.tsx:432-441` moves MapLibre imperatively but does not
  update or invalidate that ref.
- `src/components/MapView.tsx:1127-1165` uses the stale ref as the origin of
  the next progress-driven camera update.
- `e2e/travelback.spec.ts:2590-2710` proves the camera changes while paused but
  stops before playback resumes, so it cannot detect the handoff.

Concrete failure: pause at a seek-snapped nonzero point in an Orbit scene,
change duration by an amount whose bearing delta is below the 120-degree snap
threshold, then resume. The duration handler moves the map to the exact new
camera, but the first resumed progress update blends from the pre-change
camera kept in `lastCameraStateRef`. With progress `0.55`, rotation speed
`36°/s`, and duration `30 → 35`, the imperative update advances bearing by
`99°`; the first scene-smoothed frame starts only 70% of the way from the old
authority and therefore visibly jumps roughly `30°` backward before
converging. The same authority split exists for transition and scene preview
publication through the same handle.

Fix: make `applyCameraState` reconcile the smoothing authority with the pose it
actually publishes (store a cloned state, or invalidate the ref so the next
declarative update snaps from current ownership). Add a paused
duration-change-then-resume regression below the large-bearing snap threshold.

This is not the Cycle 10 stale-paused-camera root: the paused update now occurs
immediately and correctly. The new failure is the subsequent imperative-to-
declarative ownership handoff.
